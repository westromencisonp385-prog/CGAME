# 《挖掘机拯救世界》美术与音频生产计划

版本：2026-09-20 · 与 `game-design.md` 的首发上限对应。所有数量、面数和工时是制作预算初稿，垂直切片后按实测修订。

当前整体方向以 [美术方向 A](assets/art-direction.md) 为提案，待用户确认。Image2.5目标位图 + Godot原生特效生产见 [资产制作规范](assets/production-guide.md)；开工遵循 [需求索引](requirements.md) 的G0→G1→G2→G3。下面保留旧容量估算，不代表已批准批量制作。

## 1. 视觉方向

现役提案采用**斜俯视3D、宽大机械体块、有限色板、受控明暗、荒唐工业童话**。整蛊通过工程因果、尺度差和身体语言产生；车辆要有力量与可操作感。完整构图、材质、喜剧和UI规则见美术方向文档，先整体确认再制作单件内容。

色板以现役美术方向文档为唯一来源；本文件旧色值停止作为制作标准。颜色必须配合形状、运动和图标，避免仅靠红绿区分安全与危险。

辨识顺序：挖斗和驾驶室 → 当前副工具 → 敌方危险区 → 可挖资源 → 修复设施 → 装饰。植被与建筑不得持续挡住玩家、抛射物或首领预告。粒子不覆盖命中窗口；大爆炸可壮观，但中心轮廓和躲避路线必须保留。

材质以共享色板/少量图集、顶点色和简单粗糙度为主。磨损只放在近景可读的关键边缘，普通环境不逐件绘制高精度贴图。所有核心内容先在真实游戏镜头下评审，不能只看 Blender 转台。

## 2. 造型语言与世界变化

| 对象 | 形状原则 | 动作/表现原则 |
|---|---|---|
| 玩家 | 宽履带、醒目驾驶室、夸张主斗；模块有各自剪影 | 起步压低、刹车回摆、铲击短蓄力后利落接触 |
| 普通敌人 | 每类一个明显特征：盾面、喷罐、尖钻、轮缘 | 行动前的姿态比装饰重要，受击可短时失衡 |
| 首领 | 大质量体块、能拆解的危险部位、明亮弱点 | 预告→攻击→失衡三段读图一致 |
| 可挖废料 | 带可识别的资源边缘和松散轮廓 | 被铲后少量碎块、收拢流线与地块显露 |
| 修复节点 | 统一青色可交互标记，群系外形不同 | 启动声、灯带、连续地表变化联动 |
| 已修复环境 | 更多柔和曲线、绿植和流动细节 | 风、水、鸟群少量点缀，不增加模拟负担 |

地块采用“污染 / 清理 / 修复”三态。主要变化由颜色混合、低成本植被实例、预制前后态和受控水面动画完成。只给关键地标制作独特修复动画。世界地图用同一套三态语言，与关卡保持一致。

## 3. 资产清单与数量上限

数量按独立模型/设计定义计，材质换色、简单尺度变化与升级数值不算新资产。拆件共享、LOD 与碰撞体是同一资产的交付内容，不再当作额外“内容量”。

### 车辆与战斗

|---|---:|---:|---|

## 4. 动画与音频

车辆不需要写实人体动作库。优先采用独立机械节点、程序旋转和少量关键帧；主挖臂包含转台、动臂、斗杆、铲斗，液压杆只做视觉跟随。挖掘、战斗和投掷使用共用动作片段与不同命中参数。

必需动作：待机液压抖动、起步/刹车倾斜、履带/车轮运动、瞄准旋转、铲击预备/接触/回收、装料、投掷、受击、过热、体量扩张、报废。普通敌人每种约 4–6 个基础动作/姿态；首领按攻击基元共享预告节奏。

| 音频类别 | 垂直切片 | 正式版计划 | 制作重点 |
|---|---:|---:|---|
| 载具与机械声音事件 | 10 | 18–24 | 履带、发动机/电机、液压、转台、作业工具，不疲劳的循环层 |
| 接触/战斗声音事件 | 12 | 24–32 | 土石、金属、命中、破甲、投掷、爆炸；常听事件有3–5变体 |
| 世界与任务声音事件 | 6 | 12–16 | 污染风声到鸟鸣水声的变化；设施成功提示清晰 |
| UI声音事件 | 6 | 8–10 | 确认、取消、升级、错误、奖励、存档等 |
| 音乐主题 | 2 | 5–6 | 车库、3群系、首领/终局；战斗层与修复层共享主题 |
| 人声 | 电台短声 | 非语义电台音/少量关键短句 | 首发正文以简中/英文字幕为主，不规划全剧情配音 |

声音事件与音频文件数分开：一个金属命中事件可能含多个文件和随机音高。自动武器须限制并发音源；主挖斗、危险预告、首领弱点和修复完成优先。输出峰值、响度、音乐/效果/界面分轨与暂停行为统一校验。

## 5. 工程交付规范

建议 Blender 制作源文件，以 `.glb` 导入 Godot。工程单位 1 米；源文件应用缩放；对象以清楚的本地原点与朝向交付；导入朝向、坐标和比例必须由一辆试验车先校准，之后写成导出预设。

模型命名示例：`veh_excavator_base_a`、`tool_breaker_a`、`mod_cooler_a`、`enemy_charger_a`、`env_river_pipe_straight_a`。每件资产有稳定 ID、源文件、导出文件、作者/授权、尺寸、碰撞策略、材质槽、LOD策略及使用位置。

附件接口统一命名：`socket_arm`、`socket_tool`、`socket_support_l`、`socket_support_r`、`socket_fx_exhaust`。尺寸包围盒、主斗触达范围和镜头遮挡测试先冻结再外包；不能美术交完后才发现插槽方向不一致。

| 资产等级 | 首轮预算建议 | 适用说明 |
|---|---|---|
| 玩家完整装配 | 约 10k–20k 三角面 | 主体、挖臂和模块合计；先保证轮廓与动作 |
| 普通敌人 | 约 1k–4k 三角面 | 密集单位用更低LOD或简化模型 |
| 首领 | 约 15k–30k 三角面 | 拆件与碰撞数量同样受控 |
| 环境小道具 | 约 100–1.5k 三角面 | 大量重复对象尽量共享材质/实例化 |
| 贴图 | 512–1024 常规，主视觉可2048 | 不为每个小物体单开高分辨率贴图 |

这些是风格与性能起始预算，不是帧率保证；材质切换、阴影、粒子、碰撞和可见数量都要在目标硬件测量。场景使用有限真实阴影、受控透明特效、实例化植被；破坏碎屑有数量上限和生命周期。完整渲染路线由技术架构文档决定。

每件可交付资产应过六项验收：实际镜头可辨认；比例/枢轴正确；碰撞不妨碍驾驶；材质与色板一致；暂停/受击/修复状态可读；导出文件与源文件及授权记录齐全。模型漂亮但挡视线或影响判定视为未完成。

## 6. 生产顺序与外包边界

1. **灰盒：** 主车、主斗、废料块、三类敌人、一个修复节点。此时重点是输入、速度、铲击和镜头，临时材质即可。
2. **风格样张：** 一辆完整阶段II挖掘机 + 1个工具 + 2种敌人 + 河谷小景 + 污染/修复对照。所有对象导入实机后一起评审。
3. **垂直切片：** 完成第一群系必要资产、首领与全流程UI。录制30秒无剪辑画面，检查混战和最大体量，而不是只看空场。
4. **模块化扩产：** 冻结接口和美术模板，再做其余群系、工具与敌人。每一批有可玩合同接收，避免仓库里堆大量未集成模型。
5. **发布整饰：** 统一材质/音量/UI，补商店图、首尾与关键过场；最后进行本地化、性能、输入与存档回归。

适合外包：主车辆定稿、关键首领、统一风格的图标包、商店主视觉、机械声音与音乐母版。个人/AI更适合：灰盒、资源定义、资产验证脚本、参数变体、关卡块组合、可重复的导出工作与文档。AI生成图可作为概念探索，但应经人工统一结构与风格后再进入模型制作；不能把互不一致的概念图直接当作可用资产。

外包第一批只买“一辆车+一套小景”的风格与接口样张。合同交付写清源文件、商业使用范围、修改权、第三方素材清单与验收返修；后续按单批可验收资产下单。具体报价需询价，不能把下列工时当成市场定价。

## 7. 工作量预算与减配规则

以个人主导、部分外包为前提，正式上限的视觉与音频工作量初估如下。这里的“人日”包括制作和自检，不直接等于日历天；大量集成与游戏测试还在总项目工期内。

| 工作包 | 初估人日 | 主要不确定性 |
|---|---:|---|
| 风格探索与导出规范 | 8–12 | 初次定风格与返工次数 |
| 主车、模块与机械动画 | 20–30 | 挖臂质感与成长装配兼容 |
| 敌人与首领 | 20–32 | 首领是否需要独特复杂动作 |
| 三群系环境与任务设施 | 24–36 | 地块复用程度与修复效果 |
| UI、图标与少量叙事图 | 14–22 | 小屏可读与中英文排版 |
| 玩法特效与修复表现 | 10–16 | 密集战斗中的透明效果开销 |
| 音效与音乐 | 12–20 | 原创比例及外包修改轮次 |
| 商店素材与宣传剪辑 | 6–10 | 主视觉定稿、截屏与实机剪辑 |
| 合计，未加机动 | **114–178** | 应再预留约20%的集成/返工空间 |

这说明美术与音频本身就足以占据数月产能。总体 12–18 个月的估算必须包含程序、关卡、试玩、发布与外包等待，不能把模型数量除以AI生成速度当作日历。

减配时保留：主车手感、主斗动画、首领预告、修复对比、UI可读性、基本音频反馈、完整结局。依次减少：世界插画 → 装饰小道具 → 底盘外观数 → 非核心工具 → 第三群系。可售减配版对齐游戏设计：2群系、6合同、2底盘、4工具、6模块、2区域首领及组合终局。

## 8. 资产台账模板

后续资产管理使用表格或CSV，字段统一为：

`asset_id, category, biome, display_name, priority, source_path, export_path, author, license_record, status, version, owner, review_scene, estimated_days, actual_days, notes`

状态只用 `planned → blockout → review → approved → integrated`；`approved`代表外观和文件检查通过，`integrated`才代表游戏里可用。首发清单逐项走完，避免只有文件、没有实际接入。Wanderburg 的安装素材用于观察实现特征和体验，不列入本作资产台账、不直接复制到可发布工程。
