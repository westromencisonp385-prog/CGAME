# Weaver/VISVISE API 的真实用途与 CGAME 接入边界

这份说明根据本地 `weaver-api-docs.md` 和本次可重复调用结果整理。它修正一个关键误解：Weaver 是一组异步 3D 处理服务，不是“输入一张概念图就得到可直接进游戏的最终资产”的自动美术总包。

## 它擅长什么

| 阶段 | 接口 | 真正产物 | CGAME 的用法 |
|---|---|---|---|
| 输入整理 | 去背景、风格化、去花纹 | 处理后的图片/2D资产 | 只整理输入，不等于风格定稿 |
| 视图补全 | 图生360（7） | 四视图和任务资产 | 给建模服务提供视图，不能替代人工设计 |
| 草模生成 | 图生高模（3）、中模（11） | 一个或一组 AI 网格候选 | 快速得到形体草模；之后必须拆件、重命名、补材质和接口 |
| 几何处理 | 重拓扑（1）、布线重建（10）、LOD（2） | 处理后的网格文件 | 在已有模型上降面/整理拓扑；不负责玩法结构 |
| 表面处理 | UV（9）、2UV（15）、贴图纹理（8） | UV/贴图/材质候选 | 只在不会破坏作者化色块时采用；检查 UV、颜色和材质槽 |
| 角色化动作 | 骨骼架设（5）、蒙皮（6） | 带骨骼/权重的模型 | 只对服务支持的模型类别和输入格式尝试 |
| 动作候选 | 视频/文本生动画（4）、图生Pose（12） | FBX/BVH 或候选动作包 | 人物/四足动作候选；工程车机械动作仍由枢轴和关键帧控制 |
| 2D编辑 | 2D拆分（14）及组件操作 | 分部件2D资产 | 从多视图中取部件，再回到模型生成；不是自动理解游戏挂点 |

## 它不保证什么

服务端成功只表示算法任务完成。接口不会自动保证：

- 独立的底盘、模块、碰撞代理、挂点、状态层和 Godot 节点命名；
- 原画中的作者化比例、手绘笔触、色块规则和喜剧身体语言；
- UV、纹理、材质槽、LOD、骨骼和动作同时存在；
- 非标准工程车拥有可用骨骼，或文本动作能正确驱动液压臂、颚、阀轮；
- 生成网格与 F-05/F-12 的权威事件、碰撞和存档状态一致。

本次实际证据：第一批图生高模任务成功后，A01/C04 是单节点单网格、单材质、无 UV、无动画；B01 FBX 也没有 armature/action。它们只能作为草模候选。作者化 B01/C04 GLB 经过 Blender 检查后分别为 660/740 三角、5/6 材质，并保留命名动作；这类结果才适合作为 CGAME 的风格控制组。

## 正确生产链

1. 先由 CGAME 的风格锁定和 Blender/Godot 结构合同确定大形、拆件、枢轴、材质和动作语义。
2. 如果缺少可旋转草模，用 360 → 高模/中模获取候选；把任务当作形体参考，不把输出直接接入游戏。
3. 对已有作者化 GLB，用 UV/LOD/重拓扑做候选处理；逐件与原模型比较 UV、材质、层级和动作是否被破坏。
4. 只有 B01 这类服务支持的四足/角色化输入才尝试骨骼、蒙皮和文本动作；输入格式错误就停止，不猜参数。
5. Blender 修复和重建最终层级、材质、LOD、碰撞和动作；Godot 订阅 F-12 事件并做真实镜头验收。

## 本次调用结论

- A01 API 候选：形状能保留大嘴，但仍是单网格、无 UV、无动画，拒绝作为最终资产。
- B01/C04 作者化资产：UV 和 LOD 服务可以成功生成候选；B01 的骨骼任务以 `992103 / Input format error` 失败，说明 GLB 直接喂给当前骨骼服务不满足输入合同。后续若继续，应按文档转换为带正确 JSON 的 FBX zip，再验证。
- 机械玩家车和设施的正式动作不应依赖 text-to-motion；应使用 Blender/Godot 的命名枢轴和关键帧，Weaver 只承担能证明有收益的几何处理。
