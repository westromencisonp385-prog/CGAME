# 《挖掘机拯救世界》开发路线与交付门槛

2026-09-21更新：已有M0白模。当前下一步改为 [需求拆分](requirements.md) 的G0整体美学确认→G1实机样板→G2可玩喜剧表现→G3扩量。先完成 [方向设计](assets/art-direction.md)，不直接执行下面历史排期中的成套资产数量；完整产品范围以 [现役规格](spec.md) 为准。

状态：立项估算；2026-09-20。基线为**个人负责制作与决策 + AI 辅助实现 + 必要美术/音频/测试外包**，玩法方向为爽快战斗、挖掘升级和世界修复。以下月份不是承诺日期；尚未测得个人产能，先用前 2–3 周原型检验。设计范围见 [游戏设计](game-design.md)，技术执行见 [技术架构](technical-architecture.md)，美术任务见 [美术制作](art-production.md)。

## 1. 交付规模与取舍顺序

首发上限按设计稿：3 个群系 + 复用资产的终局，9 个合同 + 1 个终局；3 个共享架构的底盘、6 个作业工具、8 个辅助模块、约 30–36 个升级定义、8 种普通敌人、3 个区域首领 + 1 个组合终局。具体体验时长由合同节奏与试玩结果决定，不通过堆重复战斗凑时长。

这些是**内容上限，不是同时开工清单**。先做 1 底盘、主挖斗、1 可换作业头、2 模块、3 敌人、1 群系片段、1 首领原型及一个完整合同，证明全部系统能闭环。其余内容在切片通过后批量生产。

个人制作底线：

- 底盘共享控制器、骨架/转轴和插槽，差异来自轮廓、重量、速度、容量与技能倾向。
- 敌人共享移动、感知、伤害、死亡和攻击基元；首领复用清晰预警/蓄力/执行/恢复状态机。
- 地图使用手工设计的关键区块、有限重组和浅层可清障地面，不做大开放世界、任意体素挖掘或完整车辆模拟。
- 先做完整单人游戏。联网合作、自由建造、Workshop、驾驶舱、天气生态、实时水体和移动版不进入首发。

若切片后的测算超过个人能力，优先降为 **2 群系、6 合同、2 底盘、4 工具、6 模块、2 首领 + 组合终局**；保留开场、成长、营地变化、最终战与结局。先砍平行内容，不砍存档、手柄、读档恢复和完整结尾。

## 2. 12–18 个月的个人制作估算

下表以每周有稳定开发时间、可采购外包、素材规范较早冻结为假设。各阶段可部分重叠，总区间含返工与约 20% 左右缓冲。若是兼职，每周有效工时减半不能仍沿用同一日历。

| 阶段 | 时间窗口估算 | 交付物 | 通过门槛 |
|---|---|---|---|
| M0 手感与风险原型 | 第 1–3 周 | 灰盒挖掘机、主斗、搬运/投掷、3 档体量、少量敌人、基本修复反馈、基准场景 | 陌生玩家能明白“开过去、铲起、砸下、变强”；驾驶/瞄准同时可控；性能瓶颈可解释 |
| M1 可恢复的完整小合同 | 第 4–8 周 | 10–15 分钟合同、升级选择、胜负、营地、存档事务、键鼠/手柄、首个 Windows 导出、Steam 兼容试验 | 从启动到结算再开一局全通；进程中断不重复领奖；导出包独立运行 |
| M2 垂直切片 | 第 3–4 月 | 一段达到目标美术品质的群系、一个首领、音效/音乐/界面、世界修复前后、外部试玩包 | 有可录制的连续实机片段；玩家愿意重玩；能估算每合同/敌人/工具的人日成本 |
| M3 系统冻结与内容量产 A | 第 5–8 月 | 第一/第二群系主体、工具与模块主要组合、长线修复链、难度曲线、首轮本地化 | 主线前半可连续游玩；工具角色有区分；新增内容主要配置，不反复改核心 |
| M4 内容量产 B / Alpha | 第 9–11 月 | 第三群系、终局、完整开场与结局；所有计划内容可用 | 从新档到结局可完整跑通，未完成资产有清单；停止增加系统 |
| M5 Beta 与发布准备 | 第 12–14 月 | 数值迭代、优化、可访问性、硬件矩阵、Steam Cloud/成就、翻译、商店与预告 | 无阻断流程/存档丢失缺陷；目标设备达标；新手无需作者指导完成首合同 |
| M6 发布候选与缓冲 | 第 15–18 月，可提前 | 审核构建、发布候选、回滚方案、补丁分支、客服/已知问题准备 | 干净安装、升级旧档、Steam 发包与商店描述一致；签字冻结版本 |

最乐观的 12 个月仅在切片证明产能、范围严格、外包交付稳定时成立。18 个月不是自动允许加内容的余量。M2 后用真实生产速度重排一次，M4 后只安排质量与发行工作。

## 3. 第一轮 2–3 周原型怎么做

### 第 1 周：挖掘机是否有独特手感

只做灰盒。一个底盘、可转动上装、两段机械臂、挖斗，一张包含路障、土堆、敌人的测试场。

完成键鼠移动/瞄准/扫击，加入一套手柄映射；实现“铲起可利用物→携带→投掷/倾倒”的完整动作。先做撞击音、短暂停顿、镜头/震动强度开关。记录控制冲突和镜头遮挡，不画主菜单大图。

### 第 2 周：升级是否改变行为

加入 3 个功能不同的升级：更重的击打、更远的作业范围、材料回收/吸附能力；给一个敌人做能被清障/投掷打断的攻击，给一个修复对象做前后状态变化。

测试“变强→敢打更大敌人/拆更硬障碍→开出新路”的循环。尝试 3 个尺寸阶段穿过同一灰盒地图，尽早发现成长与通行宽度冲突。建立作业、战斗和破坏峰值 benchmark，记录最坏情况，而不是只看空场景 fps。

### 第 3 周：外部验证与去留

邀请 5–8 位没参与开发的人，每人 15–20 分钟；作者不口头引导，观察并记录。样本小，只用于发现问题，不把它包装成市场统计。

候选通过标准：

- 大多数人 3 分钟内独立完成一次挖起/砸击/升级；失败者的原因可明确归到提示或操作，而非“需要解释整个设定”。
- 至少 3 人主动尝试第二轮/换一种升级，且能说出与普通移动射击的区别。
- 驾驶与作业瞄准没有普遍的手忙脚乱；手柄能完成全部动作，不依赖鼠标。
- 扩大车体、改变地面、打击敌人之后，碰撞与导航仍一致；帧时间问题有明确预算解决路径。

若不通过，只给 **1–2 周有假设的返工**：减少操作键、加强挖斗打击、自动辅助搬运、缩减可变地形。仍不通过则改变核心玩法或搁置商业化，不进入成套美术外包。

## 4. 模块开发依赖

```text
驾驶 + 镜头 + 输入
  → 工具动作 + 目标查询
    → 伤害/破坏/产出
      → 货舱 + 回收经济 + 升级
        → 合同目标 + 修复反馈
          → 完整 run + 营地 + 事务存档
            → 垂直切片
              → 多群系/工具/敌人批量生产
                → 全程数值/性能/平台验收
```

以下任务必须提前并行，但不需要增加永久开发成员：

| 工作流 | 最早启动 | 依赖与产出 |
|---|---|---|
| 美术风格试作 | M0 后半 | 先做一张实际镜头下的风格场景，不先采购几十个不匹配模型 |
| 主角与插槽规范 | M1 | 由可用控制原型给比例/可达范围，外包输出英雄资产和变体规范 |
| 音频试作 | M1 | 以液压、履带、挖掘材质和投掷撞击为第一批；切片证明混音 |
| Steam 导出链路 | M1 | 实际导出包验证插件、Overlay、初始化和离线运行 |
| 数据与资产验证器 | M1 | ID、引用、升级依赖、插槽与导入规则；减少后续批量错误 |
| 商店素材准备 | M2 | 有稳定美术和真实可玩片段后录制，文案描述已经实现的核心 |
| 翻译准备 | M1 设 key，M4 文本锁 | 先中文/英文开发文本与字体测试；最终翻译由人工审校 |
| 外部测试 | M0、M2、M4、M5 | 每轮有特定问题和修复验收，不仅收“好不好玩”评价 |

## 5. AI、本人和外包如何分工

**本人负责**产品取舍、手感决策、每日整合、资产验收、试玩观察、版本发布与预算。AI 可以提高实现速度，但不能替代作者对玩法乐趣和最终质量的判断。

**适合 AI 的任务**：已定义接口的模块实现、数据迁移、编辑器辅助工具、参数表验证、自动导出、测试场景、故障定位、文案初稿、候选方案比较。每次任务限定所有权和完成条件；合入前要求可复现的验证。

**优先外包**：主角挖掘机与工具的统一模型/绑定、关键首领、核心音效包、Logo/商店主视觉、预告剪辑与最后的翻译审校。先委托一个可验收样件，再量产；合同写明源文件、修改次数、商用授权、风格与交付格式。

**AI 生成视觉的用途**：方向探索、情绪板、临时占位、方案讨论。正式 3D 资产仍需统一拓扑、枢轴、插槽、材质、动画与导入检验，不能把多张风格相近的图当作可生产资产管线。

可同时拆的任务是“资源定义校验器”“存档迁移测试”“一个独立敌人场景”“一组限定插槽的工具模型”。不要让多个代理同时改主场景、全局类型、project.godot 或一份战斗控制器。

## 6. 每个阶段需要怎样的验证

| 门槛 | 必做检查 | 失败时的处理 |
|---|---|---|
| M0 手感 | 陌生试玩、键鼠/手柄、成长碰撞、基本帧时间 | 有假设返工一次，仍失败改方向 |
| M1 工程 | 独立导出、全部胜负出口、结算时强杀进程、A/B 槽恢复、升级数值 | 修基础流程，不生产第二群系 |
| M2 切片 | 真实品质、10–20 分钟节奏、全部操作提示、外包返工量、目标硬件初测 | 调整首发规模和资产规范 |
| M3 量产 | 数据验证、组合边界、存档向后兼容、每周全程冒烟 | 暂停新增工具，先修系统性错误 |
| M4 Alpha | 新档到终局完整跑通、所有合同结束路径、世界修复状态一致 | 冻结加功能，优先阻断缺陷 |
| M5 Beta | 玩家引导、数值、性能、字体/本地化、输入、云存档分叉 | 削减特效/并发/非核心内容，保完整体验 |
| M6 发布 | 干净安装、旧档升级、Steam 启动/更新/离线、商店实机一致 | 延迟发版，不以补丁承诺绕过存档问题 |

性能验收采用 [技术架构中的固定 benchmark](technical-architecture.md#8-性能预算与-benchmark-验收)，所有数值必须注明硬件与构建。存档至少覆盖“pending 前崩溃、pending 后崩溃、commit 后但界面前崩溃、重复回调、最新槽损坏、旧版本迁移、离线成就重试”。

## 7. Steam 工作不应留到最后

- M1：导出可运行 Windows 包，建立版本号/日志；在具备开发环境与 App ID 时验证 GodotSteam。没有平台凭据也能先验证 OfflineAdapter 和普通导出。
- M2：形成能代表最终品质的截图/实机视频，准备商店页与愿望单积累。试玩反馈仍可能改变内容，避免过早承诺未完成系统。
- M3/M4：当一个完整合同已稳定，才考虑公开 demo/Playtest；demo 的存档目录、解锁边界、向正式版迁移策略需提前决定。
- M5：接好成就、云存档、控制器标签、语言、硬件要求、许可证说明；测试包从 Steam 客户端下载运行。
- M6：给审核、修改、重新上传和版本冻结留出实际缓冲。Steam 官方目前有缴费后 30 天和 Coming Soon 至少两周等要求，发布前再次核对。[Steam Direct 官方流程](https://partner.steamgames.com/steamdirect)

默认以完整单机正式版为目标。只有内容确实适合持续扩展、社区测试能帮助迭代且已具备稳定核心时，再评估抢先体验；它不是未完成主线或不稳定存档的解决办法。

## 8. 若未来组成 2–4 人团队

这是另一个资源情景，**不是当前排期假设**。稳定协作的 2–4 人小队可参考 8–12 个月范围，但增员初期存在沟通、集成和资产规范成本，不能把个人排期直接除以人数。

| 人员 | 建议职责 | 对进度的主要帮助 |
|---|---|---|
| 2 人 | 主程/玩法 + 3D/技术美术；音频/发行外包 | 代码与资产并行，切片后量产加速 |
| 3 人 | 加内容设计/关卡/测试 | 合同节奏、地图和数值不用全部挤占主程时间 |
| 4 人 | 再加程序/QA/制作中的实际短板 | 用实测瓶颈决定，不因人数增加扩主线规模 |

M0 手感门槛、事务存档和 M2 产能复盘仍然必做。团队增加后优先缩短交付与增加质量缓冲，不自动追加第四群系或多人模式。

## 9. 每周管理节奏与完成定义

每周只设 1 个面向玩家的可运行成果，例如“能开挖掘机清出路并获得一次升级”，而不是“实现 12 个类”。周初拆接口与资产依赖，周中整合，周末导出、试玩、记录缺陷并重新排序。主干始终保留一个可运行版本。

一个任务完成须同时满足：功能进入实际游戏流程；键鼠/手柄路径合理；数据与错误状态可处理；该保存的状态能恢复；资产已入台账；适用的验证通过。代码能运行但没有声音反馈、没有出口或退出会丢进度，不能算完整模块。

本轮立项后的第一项执行应是 **M0 灰盒手感原型**，不是先搭所有经理类或批量买美术。只有它证明“挖斗本身好玩”，后续独立游戏规模的投入才有可靠基础。
