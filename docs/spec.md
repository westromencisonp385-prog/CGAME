# 《挖掘机拯救世界》：幻想载具与模块构筑规格

版本：0.4，2026-09-21。按 to-spec 模板综合对话、现有 M0 与本地参考包证据；新增喜剧调性、功能/表现拆分和从整体到局部的美术关口。

状态：本地现役规格；用户已确认完整玩家流程验收和本地交付。M0 已有可运行白模、六组逻辑测试与七场景GPU截图流程，GM和原生特效已有技术样件。当前重点是需求拆分与整体美术设计，风格方向待用户确认；不把逻辑测试或生成概念图称为美术验收。规格是目标合同，未发布线上 issue，也未把所有产品要求标为完成。

## Problem Statement

用户希望个人主导、AI 协作并按需外包，制作一款可以在 Steam 发行的原创独立游戏。参考 Wanderburg 的重点是载具成长和模块组合如何共同改变操控、数值、Prefab 结构与美术反馈，而不是把移动城堡替换成现实挖掘机模型。

已有立项文档提供了合同、修复世界、技术栈和资产数量建议，但对模块的处理偏保守：主要是一个自动副工具与几个辅助加成，底盘也局限在履带、轮式、重装等现实分类。这种方案不足以承载用户明确提出的 fantasy：从一台熟悉的小工程车，成长为能吞噬敌群、改造战场、突破常识的幻想机器。

同时，现有研究深度不足以声称理解了 Wanderburg 的全部实现。已读取的发布包元数据、导出 Prefab 和脚本签名，能够说明资源组织、部分装配结构与数据字段；它们不能证明运行中的数值计算顺序、实际联动强度、抽选概率或操控手感。原创M0已运行，完整模块矩阵与参考游戏动态验证仍未完成。

用户明确指出当前视觉只能作为白模，并要求整蛊、搞笑、有趣的整体调性。现有画面没有建立成熟的构图、造型、明暗、材质和界面体系。继续逐件加贴图或特效会扩大风格不一致；需要先以解包视觉证据形成全局美学方向，确认后制作实机样板，再进入正式内容生产。

需要一份能指导研究、原型、内容生产与验收的规格：明确哪些是用户确认的目标，哪些是设计提案；让“模块如何改变游戏”成为第一条开发主线，并把尚未验证的设想留在可测试的范围内。

## Solution

制作一款 3D 斜俯视的单人载具动作 Roguelite。玩家用工程动作取得力量：铲起、吸入、压缩、投掷、钻穿、冲撞、展开和修复。模块组合改变这些动作之间的关系，让车辆在一局中从小型挖掘机发展成具有独特轮廓、驾驶节奏和战斗规则的幻想机器。

核心承诺是：**玩家安装一个关键模块后，操作方式、战术选择和屏幕上的机器都发生可感知的变化；组合后出现单件模块无法提供的玩法。** 数值增长服务这个承诺。修复世界提供战斗中的补给、捷径与安全空间，并在胜利后成为可持续看见的成果。

新增调性承诺：**玩家能用可靠的操作制造荒唐、强大、可以再次尝试的工程结果。** 整蛊来自铲、吸、压、扔、撞、修的因果与尺度反差；声音、姿态和世界反应完成笑点。推荐整体美术方向为“一本正经的胡闹工程队”：宽大机械体块、受控色板、清楚的明暗、局部夸张与明亮复苏。该具体视觉方向仍待用户确认。

### 玩家体验

一局从选取初始构筑开始。玩家驾驶小车进入废土，用基础挖斗打通出路、对抗小型敌人，回收的废料提供成长。第一次关键选择应在约 60–90 秒内发生。选择界面展示安装前后轮廓、动作变化、数值变化、代价和已激活的组合；确认后立刻有可测试的目标。

中期车辆扩大工作范围或展开新结构。玩家根据构筑选择贴身冲撞、聚怪投掷、铺设状态后连锁攻击等路线。修复设施打通下一片战场，并提供短暂缓冲。首领综合考验已有动作。胜利后保留蓝图和世界修复，局内临时成长重置；失败解释原因并保留既有永久进度。

幻想可以非常夸张，但仍通过工程动词让玩家理解。例如磁暴鲸口把一群机器压成炮弹，地脉钻龙沿预告路线钻穿战场，折叠堡垒展开巨型装置。它们是候选方向，不是本轮全部开工的资产清单。

首个喜剧切片建议“鲸口打包”：小敌机拼命倒车仍被聚拢，大颚将其打包成保留小旗的废料块，玩家投出后顺手启动一台需要巨型扳手的水泵。目标资格、压缩与投掷结算是功能需求；履带挣扎、颚部动作、小旗落下和修复余韵是表现需求。现有磁吸/载荷不代表这一整段已经实现。

### 本轮规格对应的交付层次

| 层次 | 要证明的体验 | 范围 |
|---|---|---|
| 研究基线 R0 | 对参考模块的判断有逐项证据 | 模块/升级/载具矩阵、引用关系、样例装配结构；不能把空方法体当算法 |
| M0 构筑原型 | 模块让同一辆车玩起来不同、看起来不同 | 一场约 5 分钟灰盒、三套组合、一个修复节点、可重置对比、键鼠/手柄、基本音画 |
| G0→G2 美术关口 | 原创风格与幽默在真实镜头和操作中成立 | 全局方向确认后，一车、一敌、一段河岸、一个修复设施与一条喜剧动作；与M0/M1并行，不等到M2才定风格 |
| M1 完整小合同 | 构筑能进入一个完整且可恢复的游戏流程 | 出发、目标、升级、首领、胜负、营地、安全检查点、独立 Windows 导出 |
| M2 垂直切片 | 模块幻想在目标美术品质下成立 | 一个群系、一条完整合同、代表构筑、首领、界面和修复前后对照 |
| 完整版 | 多次出车与战役结局均有价值 | 内容量以 M2 实测产能重新冻结；平台、优化、本地化和发布验收不可省略 |

## User Stories

以下编号作为需求引用编号；故事覆盖完整产品，所属阶段以实施与测试决策为准，并非要求 M0 一次实现全部功能。

1. 作为玩家，我希望从一台容易理解的小挖掘机成长为夸张的幻想机器，以便每次出车都能期待新的力量形态。
2. 作为玩家，我希望挖掘机的想象力超越现实型号，以便体验到磁场吞噬、巨型展开和改写地形等不寻常能力。
3. 作为玩家，我希望模块改变动作和战术，以便选择构筑时有超越伤害数字的判断。
4. 作为玩家，我希望安装不同模块后车辆轮廓能看出区别，以便看见自己的选择和成长。
5. 作为玩家，我希望驾驶有重量但响应清楚，以便在危险中精确调整位置。
6. 作为键鼠玩家，我希望能边驾驶边调整作业方向，以便用走位创造有效铲击角度。
7. 作为手柄玩家，我希望关键动作和所有菜单均可完成，以便无需切换鼠标游玩。
8. 作为玩家，我希望冲刺、转向、刹车和装载能形成战术取舍，以便移动本身参与构筑。
9. 作为玩家，我希望主挖斗同时用于清障与战斗，以便持续感到自己在操作工程机器。
10. 作为玩家，我希望铲起块料并投掷时有明确的准备、接触和释放反馈，以便掌握距离与时机。
11. 作为玩家，我希望空料斗时仍能攻击，以便投掷资源耗尽不会使车辆失去基本能力。
12. 作为玩家，我希望关键路线不依赖抽中特定稀有模块，以便任何正常构筑都能完成主线。
13. 作为玩家，我希望危险招式和自身特效能够区分，以便在构筑变强后仍能读懂战斗。
14. 作为玩家，我希望升级前能看到车辆外观预览，以便理解新部件装在哪里、怎样变化。
15. 作为玩家，我希望预览同时说明动作变化、收益和代价，以便不必靠猜测识别模块价值。
16. 作为玩家，我希望取消预览后原装配保持一致，以便自由比较选项。
17. 作为玩家，我希望确认安装后的实际表现与预览一致，以便相信升级界面。
18. 作为玩家，我希望已满槽位时能看见明确替换方案，以便不会得到无法使用的奖励。
19. 作为玩家，我希望冲突模块和未满足条件的组合有清晰说明，以便规划下一次升级。
20. 作为玩家，我希望一次升级至少提供一项当前有用的选择，以便不因随机结果失去成长机会。
21. 作为玩家，我希望普通强化与改变玩法的分支交替出现，以便成长既连续又有惊喜。
22. 作为玩家，我希望已投入的构筑有可预览的组合目标，以便逐步组装而不完全依赖随机。
23. 作为玩家，我希望多个模块可以通过公共状态或事件自然联动，以便发现设计者没有逐项说明的应用方式。
24. 作为玩家，我希望显著联动有名称、触发提示与结果反馈，以便理解强大效果来自哪里。
25. 作为玩家，我希望拆下关键模块后组合正确失效，以便装配规则始终可理解。
26. 作为玩家，我希望更换车辆阶段时保留合法装配和成长，以便扩张不会丢失一局的选择。
27. 作为玩家，我希望大型部件展开后改变攻击方式或路线判断，以便变形有玩法意义。
28. 作为玩家，我希望变形的过渡、代价和结束状态清楚，以便不会在不可控动画中受罚。
29. 作为玩家，我希望磁吸与宽斗组合能改变敌群分布，以便把零散威胁集中处理。
30. 作为玩家，我希望水炮造成的湿润能被电弧利用，以便用先铺状态再释放的节奏制造连锁。
31. 作为玩家，我希望惯性飞轮能把驾驶蓄势转成一次强力冲击，以便路线与撞击时机形成高风险回报。
32. 作为玩家，我希望三类代表构筑都能处理首领和工程目标，以便自由选择风格。
33. 作为玩家，我希望能力增长后能处理开局难以处理的目标，以便体会尺度反转。
34. 作为玩家，我希望热量、冷却与装载量的限制可见，以便主动管理爆发窗口。
35. 作为玩家，我希望关闭华丽特效也不改变命中和资源结果，以便按设备和偏好调整表现。
36. 作为玩家，我希望挖掘清障能打开捷径或安全位置，以便环境破坏是战术的一部分。
37. 作为玩家，我希望修复水泵、电网和道路能即时影响战场，以便建设成果不仅存在于结算图片。
38. 作为玩家，我希望修复后听见和看见世界变化，以便获得与破坏爽感不同的情绪回报。
39. 作为玩家，我希望合同具有明确主目标和有限支路，以便一局内做出路线选择而不过度跑图。
40. 作为玩家，我希望敌人和首领测试已有动作，以便胜负来自读招和构筑运用。
41. 作为玩家，我希望完成目标后获得短暂喘息，以便有时间欣赏成长与修复。
42. 作为玩家，我希望失败时能看见主要受伤来源和构筑贡献，以便决定下一局如何改变。
43. 作为玩家，我希望胜利后获得新选项而非必须刷取的永久倍率，以便不同尝试本身有价值。
44. 作为玩家，我希望世界地图持续显示已修复地区，以便理解整个战役的进展。
45. 作为玩家，我希望挑战重玩不破坏已完成的修复，以便保有拯救世界的成果。
46. 作为玩家，我希望战役有开场、推进、终局和结尾，以便买到一个完整体验。
47. 作为玩家，我希望安全检查点明确提示保存内容和恢复位置，以便理解退出的影响。
48. 作为玩家，我希望异常退出后装配、资源和修复记录保持一致，以便不丢失可信进度。
49. 作为玩家，我希望重复打开结算页不会重复发放或扣除奖励，以便进度稳定。
50. 作为离线玩家，我希望 Steam 服务暂时不可用时仍能继续单人流程，以便平台故障不阻断游戏。
51. 作为多设备玩家，我希望存档冲突保留可选分支并说明进度，以便避免静默覆盖成果。
52. 作为玩家，我希望重绑定输入、调整字幕、界面大小、震动和闪光，以便选择舒适的游玩方式。
53. 作为简中或英文玩家，我希望组合说明和数值预览在自己的语言中清楚完整，以便理解构筑决策。
54. 作为目标设备玩家，我希望激烈战斗、巨型变化和连续清障仍保持可读且稳定，以便爽感不被卡顿打断。
55. 作为设计者，我希望模块矩阵把已验证事实、推断和缺失数据分开，以便不把导出痕迹误当运行规则。
56. 作为设计者，我希望调整同一套模块数据就能更新候选、预览、实战和统计，以便避免多套数值漂移。
57. 作为美术制作者，我希望清楚知道每个模块的轮廓、等级状态、接口和反馈要求，以便制作的资产能直接进入体验。
58. 作为开发者，我希望替换部件失败时仍保留旧的合法装配，以便资源缺失不会损坏一局。
59. 作为开发者，我希望组合触发有来源和递归边界，以便复杂联动不会造成重复伤害或无限触发。
60. 作为制作人，我希望先用少量模块验证组合深度与制作成本，以便在投入整套美术前决定范围。
61. 作为制作人，我希望原创模块能追溯到明确的解包结构观察，以便将研究转成挂点、等级和反馈要求。
62. 作为美术制作者，我希望图像提示词、结果与实际模型版本分别记录，以便复现素材并确认来源。
63. 作为玩家，我希望位图与 Godot 粒子、材质、几何和动画共同表达组合，以便效果随实时状态变化。
64. 作为测试者，我希望用 F1 或可见按钮打开 GM，以便不写脚本也能复现问题。
65. 作为测试者，我希望一键切换构筑、阶段、载荷和生命，以便快速比较能力。
66. 作为测试者，我希望冻结AI、无敌、慢放和恢复正常速度有明确状态，以便观察攻击与冷却。
67. 作为测试者，我希望 GM 使用独立检查点且重试清除作弊状态，以便不污染正常进度。
68. 作为开发者，我希望 UI 与自动化共用有限 GM 命令，以便一份复现步骤可供人和 AI 执行。
69. 作为开发者，我希望真GPU截图记录引擎、构筑和场景条件，以便核对shader、透明度和UI布局。
70. 作为开发者，我希望 CLI 检查完成标记和错误日志，以便退出码零不会掩盖失败。
71. 作为制作人，我希望一条项目命令能选对引擎、导入、测试、截图和导出，以便下次会话直接接续。
72. 作为玩家，我希望关闭非必要表现时玩法结果不变，以便性能设置不改变规则。
73. 作为玩家，我希望通过自己的工程操作整蛊敌人，以便笑点来自我造成的局面而非不断弹出的段子。

78. 作为玩家，我希望世界修复既带来温暖回报又有出乎意料的小反转，以便期待下一次施工成果。
79. 作为玩家，我希望连续战斗的音效和笑点有节制且有变化，以便长时间游玩不会疲劳。
80. 作为玩家，我希望实际镜头下能先看见工作头、目标和退路，以便夸张成长不会牺牲操作判断。
81. 作为玩家，我希望车辆、环境、敌人、界面和声音属于同一种美学，以便整个游戏具有明确身份。
82. 作为制作人，我希望先审阅完整场景风格板、成长剪影和色材规则，以便在正式资产开工前确认调性。
83. 作为美术制作者，我希望每项表现任务有可回查的参考事实与原创转译，以便学习参考的设计方法而不只跟随模糊印象。
84. 作为开发者，我希望改变规则的工作与只改变表现的工作分别编号验收，以便不在美术优化中意外改变命中、经济或保存。
85. 作为制作人，我希望先完成真实镜头内的一车一敌一场景样板，以便发现整套风格的问题后再扩大生产。
86. 作为测试者，我希望一键复现代表性整蛊动作并对比无特效版本，以便定位规则、动画、声音和遮挡问题。
87. 作为玩家，我希望界面保留关键信息并给战场留足空间，以便不用穿过大块说明面板寻找目标。
88. 作为制作人，我希望概念图、技术样件、正式资产和验收截图标明各自状态，以便不会把漂亮方向稿误判为已经实现。

## Implementation Decisions

### 1. 术语与当前实现状态

本仓库包含研究文档、审计工具、导出统计、领域词汇表和原创 Godot M0。已存在装配、战斗、合同重建及损坏快照恢复测试；这些测试不等于真实手柄、最终美术、Steam或完整战役验收。以下包含已有实现及后续目标，不能仅因出现在规格中就视为全部完成。

| 术语 | 定义 |
|---|---|
| 模块 Module | 可装配、具有状态与可见表现的能力单元；不能与单次属性强化混为一谈 |
| 模块类别 Family | Tool、Drive、Reaction、Repair、Morph 五类行为职责；不直接等于五种互斥槽位 |
| 槽位 Socket | 带类型、位置、空间包络与兼容约束的挂载位置 |
| 装配 Loadout | 一辆载具当前模块实例、所属槽位、升级与阶段的集合 |
| 强化 Upgrade | 对已装模块或车体的状态变化，可含数值、行为、外观或分支选择 |
| 组合 Synergy | 多个能力通过结构条件、运行状态或输出转换产生的联动 |
| 形态 Morph | 在可控范围内切换轮廓、动作或移动规则的结构变化 |
| 合同 Contract | 一段有目标、成长与成败出口的关卡内容定义 |
| 出击 Run | 某合同的一次实际游玩，拥有独立标识、随机流、资源和结算 |
| 修复 Repair | 局内改变环境或设施；胜利提交后成为永久世界进度 |

### 2. 研究证据与原创设计分层

- 参考包可验证 Unity 发布形态、导出场景、Prefab 结构、部分序列化值和脚本签名。研究矩阵必须保留来源定位、提取方式、缺失字段与置信等级。
- 接续 R0 的矩阵范围为导出中全部模块候选、其引用的升级/效果、神器候选和玩家载具阶段；分类先由组件类型和引用关系决定，再用命名辅助。不能仅以名称包含某词认定为可玩模块。
- 每条记录至少覆盖 ID、名称、槽位资格、主动/被动效果引用、冷却/尺寸/速度字段、升级与分支引用、显示层级、载具挂点及材质/音画关联。未解析到的字段记为未知，不能用零代替。
- Prefab 中存在关闭的 T0–T5 节点，只能直接证明多级资源被放在一起；如何切换必须结合序列化绑定或运行观察验证。方法名支持职责推断，不能恢复公式与调用顺序。
- 完整模块矩阵仍是待完成的研究工作，本规格不将其伪装成已经交付。研究抽取独立于原创游戏资源；本作重新实现代码、资产、命名和参数。

### 3. 技术基线

引擎更新为官方 Godot 4.7.2 stable 与同版本导出模板，沿用 GDScript、3D斜俯视、Mobile、Jolt、脚本底盘和程序机械臂。启动、测试和截图经版本固定的 CLI，系统 PATH 的旧版不决定本项目引擎。位图采用用户指定的 Image2.5 目标路线，Godot 控制实时特效，Blender/程序几何负责可旋转模型。音频用原生总线，Steam 后续经适配层接入。

这些选择用于降低制作成本，不限制机器的幻想尺度。巨型展开、磁场、浅层钻行、能量桥等可以通过受控状态、预制结构、视觉过渡和明确判定实现。每个幻想方案优先选择玩家能感到变化的实现，不把模拟精度当质量目标。

### 4. 装配拓扑与操作预算

旧提案“主斗 + 一个自动作业槽 + 两个只能装辅助件的槽”不能同时容纳水炮和电弧。本规格替换这项原型限制：

- M0 保留核心工程操作器，含基础挖斗以及宽斗等强化；可以改变其外形和动作，但基础清障功能始终可用。
- M0 提供两个通用功能挂点，可装 Tool、Reaction 或 Repair 类模块；可同时装水炮和电弧。Drive 使用一个动力接口；惯性飞轮与内置冲刺联动。
- Morph 先表示同一装配内的结构阶段或互斥姿态，M0 不再增加第四个复杂能力槽。首发槽位数量和增长路线待 M0 验证，不把这套拓扑提前宣称为终版。
- 输入保持移动、瞄准、主作业、投掷/倾倒、冲刺、交互和暂停。两个功能模块先通过自动触发、主作业命令或目标状态协作，避免水炮与电弧要求额外四个热键。该映射是原型提案，要用键鼠和手柄分别试玩。
- 模块类别、挂点类型、视觉覆盖区域和数值标签分开；对称双侧视觉不能重复注册伤害或计入两件装备。

### 5. 三条代表组合

以下行为是原创原型合同，不是对 Wanderburg 原算法的描述。参数均集中在定义数据中，M0 不锁死最终数值。

| 组合 | 单件价值与组合结果 | 成本、边界与反制 | 必须可见的变化 |
|---|---|---|---|
| 宽斗 + 磁吸 | 宽斗扩大有效铲击扇区；磁吸把可牵引的小目标拉向工作区；组合支持聚拢、装载、压缩后投掷 | 有作用距离、角度、载荷和单次目标上限；重甲与固定首领不被直接吸走 | 斗口张开、磁性组件展开、拉力方向、装载体积、压缩释放和重击声音 |
| 水炮 + 电弧 | 水炮造成带时限的湿润并具有推退价值；电弧有基础单体作用；湿润目标允许有限跳跃 | 湿润到期失效；每次连锁不重复命中同一目标，限制跳数/距离/触发次数；保留弱点阶段之外的反制 | 水束、湿润轮廓、能看清路径的电弧与清楚的放电节奏 |
| 惯性飞轮 + 冲刺 | 飞轮按有效行驶积累势能；一次满足方向和接触条件的冲刺消耗势能形成增强撞击 | 原地转圈/碰墙不能无限蓄势；冲击只消费一次；转向、刹车和冲刺资源形成代价 | 飞轮速度、储能强度、车体蓄势姿态、撞击方向和卸能反馈 |

M0 三种装配在同一个战场对比。至少一种组合在成长后具有明确的局部结构展开，不仅换颜色或把根节点放大。磁暴鲸口作为首个候选表现，可通过斗口与磁性结构实现；地脉钻龙、生态方舟、折叠堡垒等保留为后续候选，不能因列在文档中自动扩入 M0。

### 6. 系统责任与交互合同

| 单元 | 对外职责 | 关键约束 |
|---|---|---|
| ContentCatalog | 按稳定 ID 提供只读定义与验证结果 | ID 唯一、引用存在、兼容条件可解释 |
| ModuleDef / UpgradeDef / VehicleDef | 描述能力、成本、标签、升级、外观与接口 | 定义中不保存当局血量、冷却或装载量 |
| ModuleRuntime | 持有实例状态和触发能力 | 标记所属车辆、来源、升级、冷却；卸载后不残留效果 |
| LoadoutAssembler | 验证、预览、确认、替换和迁移装配 | 安装失败保留旧装配；成功只提交一次 |
| BuildEvaluator | 为预览、战斗和 UI 提供同一份属性与组合解释 | 相同输入状态得到一致逻辑结果，无重复累计 |
| SynergyResolver | 解析组合条件与有限事件转换 | 区分装配资格和临时状态，限制循环触发 |
| ModuleVisual | 呈现等级、展开、运行、命中与冷却 | 不拥有权威伤害或经济结果；表现关闭不改变模拟 |
| Vehicle / Tool / Combat / Harvest | 执行移动、作业、伤害和采集 | 判定与反馈同源；同一事件不能重复结算 |
| RunController / Repair / SaveService | 管合同、永久进度和恢复 | 明确局内/永久边界，奖励与修复提交一致 |

装配请求带车辆、槽位、模块、升级和请求标识；结果表达成功的新装配版本或失败原因。预览返回可见形态、属性差异、输入语义、已满足/未满足组合和代价，但不写真实装配、库存、随机流或存档。

装配按“验证候选和兼容性 → 在隔离环境构建候选 → 生成新属性与组合结果 → 准备视觉和挂点 → 成功提交新装配 → 释放旧订阅/表现 → 发布变更”执行。任何准备阶段失败都回滚候选，旧装配继续有效。变更在明确的模拟边界提交，避免同一物理步一半使用旧装配、一半使用新装配。

### 7. 数值、标签与触发边界

- 属性先取基础定义，合并带来源标识的加法修正，再按明确定义的乘区计算，执行转换规则并施加合法范围与下限；当局状态只在规定阶段参与。范围、速度、节奏、输出等维度不能都混成一个伤害倍率。
- 每项修正声明属性、运算阶段、来源、叠层规则和上限。装备/卸装从合法装配重算，禁止对当前值反复加减产生漂移。
- 组合分为直接条件、运行时状态条件和输出转换。永久装配标签与湿润、燃烧、过热等有时限状态分开管理。
- 触发事件携带根事件、来源模块、目标、通道和已触发规则信息。采用规则去重、最大跳数、目标上限与触发预算，阻止“命中生闪电，闪电又无限触发命中”的循环。
- 冷却变化必须定义当前进度如何保留；替换相同模块、切换形态和读取检查点不得凭空刷新主动能力。尺寸变化也不能使同一次扫击重复命中相同目标。
- 高收益可以很夸张，但必须有可见条件、代价或风险窗口。平衡目标是多种构筑都有完成能力，不追求所有武器逐秒输出相等。

### 8. Prefab、形态与美术交付

原创 Godot 载具由稳定挂点、逻辑组件和独立视觉子树组成。局部工具替换、互斥结构展开、参数化材质/粒子三种方式优先；不为所有模块排列复制整台车。

每件模块必须交付：一句幻想描述、主要动词、对应槽位与空间包络、单件玩法、组合关系、成长轮廓、动作阶段、命中/发射点、基础音效/VFX、输入提示和测试场景。等级增长可复用部件，但关键分支至少有清楚的形态或动作差异。

形态切换声明旧/新占地、工作范围、移动约束、转场时长、可取消时点和存档状态。受阻时拒绝变形或延迟到合法位置，不能让大车卡进墙体。先用预先验证的碰撞包络支持巨大视觉结构，只有玩法确实需要时才改变实际通行占地。

实际游戏镜头下优先辨认玩家核心动作、敌方危险、组合触发和修复目标。尘土、火花、摄像机反馈和音效可夸张，但不得掩盖招式。M0保留白模与临时声音作为功能对照；现在启动G0整体方向和G1/G2样板，M2扩大到完整目标品质合同。

### 9. 世界、经济与完整体验

挖掘采用有限分块覆盖层、浅层状态和可破坏物体。清障改变通路或资源分布，权威采集账与碎片表现分开。主线必经路能用基础工程能力完成，高硬度支路奖励专门构筑。

废料经验、投掷载荷、耐久和热量是局内状态；蓝图、横向解锁和已提交修复是永久状态。修复先在当局提供捷径、安全空间或补给，胜利后提交永久世界进度。失败不撤销既有成功，重玩以演练表达。

完整产品包括启动、设置、教程、装配、区域选择、合同、升级、首领、胜负、营地变化、终局与结尾。敌人围绕蜂拥、冲锋、远程、护甲、支援等行为制作，首领通过预告、执行、弱点和恢复阶段考试。局外成长优先增加可选打法，不以强制刷数值替代内容。

### 10. 保存、迁移与平台

M1 引入一个权威 envelope 保存档案和当前 run，设置独立；A/B 双槽、序号、版本、校验与备份处理损坏恢复。记录模块实例、槽位、升级、形态、资源、任务、地块差异和内容/生成版本；资源路径、对象实例号不能当持久主键。

同一结算使用唯一事务标识，按 ACTIVE、RESULT_PENDING、RESULT_COMMITTED 三阶段推进；永久奖励、解锁、修复和已提交标记一起保存，磁盘确认后才显示到账。购买、修复与合法装配持久化同样保持扣款和状态一致。

检查点描述清楚可恢复范围：保存逻辑状态与关卡差异，允许重建动态敌人，不承诺恢复每粒碎屑。M0 只验证装配快照往返，不提前实现完整商业存档系统。

Windows 独立导出从早期验证；Steam 初始化、成就与云同步经适配层，离线可继续。M1 完成兼容性试验后锁插件版本；正式版验证双机冲突、旧档迁移、手柄、Overlay 和实际客户端安装。未做 Deck 真机测试前不声称已兼容。

### 11. 制作范围与阶段优先级

先生产可复用的能力与组合，再扩群系数量。M0 允许先完成磁吸宽斗的最小纵切：装配、预览、实战、可见成长、取消/替换与快照恢复；在同一框架上再加湿润电弧与惯性冲刺。不得用只有类结构、没有实际反馈的“框架完成”作为 M0 交付。

原预算 3 群系、9 合同、终局、3 底盘、6 工具、8 辅助模块、36 升级和 8 普通敌人保留为容量情景；底盘身份优先按幻想和操作差异定义，不要求对应真实工程车型。M2 根据实际产能决定 2 群系或 3 群系方案，保护组合深度、手感、完整结尾和稳定性。

美术与音频现有估算 114–178 人日、整体 12–18 个月均是旧范围下的估算，新增形态要求需要重新测算，不能假设幻想复杂度免费。先外包一个车体与模块样件；源资产、导出、授权、插槽与实际游戏验收一起交付。AI 主要承担有边界的代码、数据验证、工具和候选方案，本人保留手感与版本决策。

### 12. 解包驱动的资产制作

每件资产走“参考事实→原创行为→位图/网格→原生表现→运行验证”链。前置炮的主动/被动发射点与等级节点、推进模块的持续/爆发VFX、迫击炮的武器/操作员层、载具阶段的剪影差异，转成明确的制作合同。记录导出对象、行号与置信等级；继承可解释的结构，所有可发布素材重新创作。

生成模型负责烟尘精灵、卡面、图标、遮罩与纹理；Godot 负责粒子数量/寿命、实时颜色、流动、闪电路径、冷却显隐、展开和声音。3D模型仍由程序几何或Blender制作，等距插画不能冒充可旋转模型或实机画面。

目标版本记为 Image2.5。当前工具没有显式版本选择器时，manifest保留requested_model与实际回执，未知就写unknown。输出需经过尺寸、alpha、边缘与实际镜头检查。首批为透明烟尘与磁暴鲸口卡面；原生效果包含命中烟尘、磁吸范围环、实际起终点电弧、水束/水雾、修复扩散环和水面流动。表现只订阅已确认动作事件，所有判定与奖励仍归gameplay；并发超额只降表现。

### 13. GM 测试工作台

开发/调试构建提供可见入口与F1；release默认禁用，普通参数不能重新开启。面板打开时阻止驾驶/攻击穿透，键盘/手柄可导航；关闭遵循原暂停状态。无敌、AI冻结、调速与测试构筑明确可见。

UI和自动化共用有限命令接口，返回成功/失败、原因和状态数据。范围包括状态查询、三构筑预设、生命、无敌、载荷/蓄势、AI冻结、0.25/0.5/1/2倍速、阶段1/2、练习目标、修复、清除敌人、重试、VFX开关和独立测试检查点。参数校验失败保持旧状态，不执行任意代码。

GM检查点与正常F5/F9分开。重试清除临时作弊状态、恢复1倍速与AI；测试出击记录不能冒充正常经济/难度数据。GM流程不另建一套绕过正式装配与目标逻辑的实现。

### 14. AI 友好的 Godot 工作流

首选版本固定CLI、可读场景/资源、公共gameplay命令和机器可读结果；LSP/DAP辅助定位。当前不引入未经核验的第三方Godot MCP桥接，必要时再评估其维护与权限边界。

导入、测试、截图、导出分别报告。超时、脚本错误、缺成功标记均为失败；不能只信退出码。headless的dummy renderer只证明逻辑；视觉验证使用真实图形设备，等待绘制结束再抓viewport，保存引擎、渲染器、GPU、场景、构筑、日志与图片路径。

固定帧/seed用于复现，不承诺跨平台物理逐位一致。fixed-fps录像不是实时性能测试；引擎benchmark-file不等于游戏帧时间分位数，性能需要单独实时采样。

### 15. 功能与表现分别立项

需求分为F功能实现与P表现优化。F改变输入语义、命中、碰撞、数值、状态、资源、流程或存档；P消费已确认的结果，改变模型、构图、材质、动作演出、粒子、声音和排版。需要新行为及演出的同一体验必须拆成F/P互相关联项，分别说明依赖与验收。

改变击退落点、命中时刻、失衡时长、可装载资格或生成物数量属于F；不改变结果的翻滚、压缩外形、回弹和落地烟尘属于P。表现需要增加事件字段或查询接口时，该缺口属于F依赖。关表现对比保持同一受控玩法输入和权威状态，不能用屏幕看着相似代替数值一致。

所有P项均带参考依据、原创转译、全局风格约束、使用场景与实机证据。参考中的序列化参数不能直接当本作最佳数值。参考未知的部分按原创设计提案验证。

### 16. 从整体美学到内容生产

美术方向先明确玩家情绪与喜剧机制，再决定世界气质、游戏镜头、主体和环境层级、剪影成长、色彩材质、灯光、动作/VFX、声音与UI，最后才冻结单件资产清单。推荐方向是有重量的夸张工业童话，主要幽默来自认真施工与离谱结果的反差。

采用G0→G1→G2→G3关口：G0交付参考证据、方向板、色材和成长规则，由用户确认调性；G1做一车一敌一段河岸与修复设施，在真实相机下先验无VFX画面；G2补足一条喜剧动作的功能差额并完成声画、GM复现与整体验收；G3才扩三构筑、完整合同与量产。这些美术关口服务M0/M1/M2，不另建一套产品阶段。

现有卡面、烟尘和原生特效是技术样件，接受新风格规则复审。场景中央保持可操作的视觉留白，玩家、危险和目标优先于装饰。基础与成长态须通过剪影和结构识别，不能只依赖发光或名称。概念图上色、光照和文字不是运行资产，也不代表渲染成本已经验证。

### 17. 喜剧、爽感与反馈合同

每个代表构筑至少设计一项可被玩家主动制造的滑稽结果，并说明准备、接触和余韵三拍。首个候选是鲸口打包；后续强制洗车、工地保龄球等根据切片表现筛选，不同时扩入近期范围。

幽默可以表现敌机慌张倒车、超大工具配小驾驶室、被压成方块后仍竖着的小旗、修泵带来过分热情的开花。它须传达明确因果，保留输入和危险反馈；装载、位移、伤害、目标完成仍遵循权威规则。演出随机变体使用独立表现随机流，不能改变升级抽选和掉落。

重复反馈有节奏和变体，主动作接触音、敌方预告与目标完成优先。笑点不要求固定次数，不以强制停顿、频繁电台段子或不可预测失控增加密度。试玩同时记录主动复现、组合解释、笑点理解和疲劳/遮挡问题。

## Testing Decisions

### 验收边界

已向用户提交的主边界为：“玩家装配 → 预览 → 确认 → 实战触发组合 → 升级/变形 → 存档恢复”。以完整 run 的公共操作和可观察结果为最高测试入口；不围绕私有方法、节点名字或信号调用次数编写镜像测试。

已有 M0 测试场及装配/战斗/合同/文件恢复公共行为测试。本轮 GM 作为同一流程的控制入口补充验证，并增加真实GPU截图。输入设备、听感与乐趣仍须实际运行和真人试玩，逻辑通过不能代替体验验收。

### 好的测试

测试必须说明玩家做了什么、应该看见或得到什么、何时不该触发。用稳定场景和可控时间验证有限行为，不要求跨平台物理逐帧一致。只有数值重算、装配一致性、触发边界、资源守恒、迁移和幂等结算等高价值风险补充窄范围测试；不为每个装饰节点或常量写测试。

### 体验门槛与性能

M0 目标为 5–8 名未参与开发者各自试玩 15–20 分钟，作者不口头解释。多数人在 30 秒内理解基础作业、3 分钟内完成一次有效成长；至少三人主动再试或换构筑，并能说明打法变化。此样本只用于发现问题，不推算留存或商业成功。未通过时允许一次有明确假设的 1–2 周修改，再决定继续、收缩或改变核心。

M0同时记录输入响应、转向过冲、漏用投掷、升级打断、看不清危险等具体问题；G1/G2开始验证视觉一致性、喜剧因果、变形冲击、连续声音疲劳和修复情绪，M2再验证完整合同。玩家幻想和乐趣不能仅由截图或性能数字验收。陌生玩家试玩尚未执行，目标标准不能写成已通过。

性能基线沿用 1080p 持续 60 fps 的候选目标、常规 30–50/压力 80 个可交互敌人、约 64 个短寿命物理碎片。作业、战斗、破坏峰值和 20 次进出场景分别记录帧时间与内存；新组合和变形必须进入压力场。所有数字注明硬件、构建、场景与预设，当前未实测，不作为最低配置承诺。
