# 资产制作：解包证据 → Image2.5 目标位图 → Godot 实时表现

2026-09-21。当前工程的资产生产规范。首批位图和原生特效是技术样件，不代表正式美术全部完成；当前3D车体仍是程序化灰盒。

**制作前置关口**：先读 [整体美术方向](art-direction.md) 和 [F/P需求拆分](../requirements.md)。当前方向 A v2 待用户确认；G0通过后先做G1镜头样板，再进入G2表现切片与批量内容。以下技术流程约束交付方式，不自动授权开始下一批资产。每件表现资产标P需求ID；涉及新规则/事件接口的差额另列F需求。

## 1. 解包是明确的结构参考

先研究一件模块如何工作，再画它的外壳。每件原创资产都要回答：装在哪里、怎样变大、什么时刻显隐、攻击从哪里出、玩家如何看懂冷却、哪一种组合会改变它。

| 直接观察到的参考 | 原创制作要求 | 本作对应 |
|---|---|---|
| FrontCannon 含 Skin、S0_Elements、主动/被动 InstantiationPoint、T0–T5、冷却层 | 交付装配根、视觉层、等级部件、独立发射点与冷却提示；完整装配预览使用同一批部件 | 主斗、磁环、水炮、电弧组件与预览场景 |
| BackDash 含主/被动 VFX、烟囱火、喷口火花和爆发节点 | 区分待机、蓄势、执行、恢复四层，持续与一次性效果分开 | 飞轮转动、蓄能亮度、冲刺尾迹、接触冲击 |
| TopMortar 同时保留炮体、升级层和操作员层 | 等级变化不只换材质；把体块变化和动画重心分开 | 磁暴鲸口的上下颚、侧翼与核心线圈 |
| Tank 阶段 0/3 的对象计数为 98/119，Spider 样例为 207 | 在实际镜头比较剪影、挂点和读图密度，不把数量当质量目标 | 低阶段紧凑车体 → 二阶段展开颚 |
| 状态反馈被单独命名，含受击、减速、无敌、吸入、行驶 | 每个效果要有触发来源、时长、终止和并发预算；关掉效果不改变结果 | NativeEffects 与 GM 的 VFX 开关 |

证据：六个代表 Prefab 的名称、行号、启用值、SHA256 保存在 [reference_asset_contract.json](../../evidence/reference_asset_contract.json)。使用 [提取工具](../../tools/reference_asset_contract.py) 可复核。导出中的节点存在和启用值是 observed；实际切换顺序、最终伤害和完整组合公式仍需要运行观察，不能按名字断言。

## 2. Image2.5 与 Godot 分工

用户指定的图像路线记为 **Image2.5**。当前内置图像工具没有公开的模型版本选择参数，因此 manifest 将 requested_model 与 actual_model 分开：前者记 image2.5，后者只填写工具实际返回的信息；未知就记 unknown。不能把普通工具回执描述成已核实的 Image2.5 调用。精确版本一旦可用，沿相同资产 ID 替换候选，不改变玩法合同。

- **生成模型负责**：风格锚点、模块图鉴/卡面、颗粒/烟尘精灵、表面纹理和明确可控的遮罩。保存原始结果、最终提示词、参考图作用、尺寸、透明度及 SHA256。
- **Godot 负责**：模型空间位置、形态显隐、轨迹、粒子寿命、速度、颜色、发光、流动、连锁路径、冷却反馈、镜头、声音和强度设置。
- **3D 几何负责**：遮挡、轮廓、真实旋转、装配、关节和碰撞包络。生成一张等距图片不能替代可旋转网格；首批仍用程序化几何，正式样件按参考图进行 Blender 建模/重拓扑后导出 GLB。

生成图上的光线仅是风格提示。不要在材质贴图上烘入本应随游戏变化的冷却、攻击电弧和界面文字。没有验证过的“无缝/透明/PBR/精确多视图”能力不能作为验收事实。

## 4. 可交付的单件模块包

每个模块的生产任务包含以下内容，缺少任一关键项不能仅凭概念图批准量产：

1. **功能卡**：主要动词、单件收益、代价、组合条件、触发/停止条件、阶段变化、输入动作。
2. **风格锚点**：Image2.5 目标提示词、允许变化与保持项、三分之四视图、小尺寸剪影、颜色材质。多视图只作为参考，机械接口由建模规范定义。
3. **结构包**：统一米制、局部朝向、根枢轴、工作头、左右挂点、主动/被动发射点、VFX与声音挂点；静态碰撞和视觉独立。
4. **状态包**：未装、预览、安装、待机、蓄势、执行、冷却、二阶段；每态说明网格可见组、shader参数、粒子和音效。
5. **效果包**：材质/粒子资源、最大并发、低画质降级、暂停/卸载清理、运行时触发源。所有表现由已确认 gameplay 事件驱动。
6. **证据包**：原始生成图、prompt、manifest、Godot资源版本、实机相机、画质、构筑、GM条件、截图/短片、缺陷与复测结论。

当前管线先固定正交斜俯视。形态尺度只改变经过验证的视觉/作业包络；需要实际扩大碰撞占地的资产必须单独做通路测试，不能把根节点无限放大。

## 5. 具体制作步骤

**0. 审阅整体方向与参考视觉。** 先确定画面焦点、形状比例、色板、材质和喜剧机制，再为单件资产指定任务。除模块结构证据外，必须使用 [参考视觉证据](../../evidence/reference_visual_study.json) 中相关观察；缺直接对应的设计标为原创提案。当前白模和旧卡面均不自动成为风格锚点。

**A. 从参考提出行为要求。** 例如 BackDash 的多组持续/爆发节点启发飞轮“常态转动→蓄势加亮→接触卸能”，不复制烟囱模型。把这些要求写进功能卡。

**B. 生成位图。** 每张只解决一件用途明确的素材。烟尘写明真实透明、无地面、无文字、边缘留白；卡面写明主体完整、背景统一、无文字，留给 Godot 绘制可本地化标签。

**C. 质量检查。** 检查尺寸、格式、alpha范围、边缘、缩小后辨识度和与现有色板的一致性；失败只针对一个问题重做。不要用模型输出的解释文本代替查看图像。

**D. 接入原生实时层。** PNG 作为粒子材质或卡面；电弧与磁场用几何/shader；网格和模型按稳定挂点装配。关掉VFX时 gameplay输出不变。

**E. 用GM复现。** 选择构筑和阶段、补足资源、冻结敌人或正常运行、调速观看接触时刻；截图同时记录GM条件，避免无敌/冻结状态被误读成真实难度。

**F. 导出复查。** 真图形运行检查 shader、alpha、UI与碰撞反馈。headless只测逻辑。正式性能评估必须实时运行，不能使用 fixed-fps录像的耗时推算游戏FPS。

## 6. 本轮表现预算

同时活动的短时效果实例先限制为20，单次烟尘最多12粒子；磁场为每台玩家车一个常驻环。超额表现允许跳过，玩法事件不能丢失。这个预算是当前代码的限制，不是目标机器实测的最低配置。

Godot 4.7.2 + Mobile 渲染器 + Jolt 是当前验证环境。GPU粒子与shader必须在该路径上实际渲染验证，Compatibility 模式仅在明确回退实验时测试，不假定所有渲染器功能相同。
