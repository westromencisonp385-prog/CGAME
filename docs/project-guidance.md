# 项目全局指导：风格化、高精度、反 AI 感与百种构筑

日期：2026-09-27。状态：用户确认的跨规格质量门。

本文是 `docs/spec.md` 的全局执行补充，不替代产品规格、wayfinder 决策路线或 F/P 需求索引。若出现冲突，以 `docs/spec.md` 为准；本文负责回答“做出来必须是什么品质、为什么不是白模、怎样让构筑真正多样”。

## 1. 四条不可退让的原则

### 1.1 风格化

视觉必须有明确的工业童话语法：夸张但可解释的比例、强主剪影、受控色板、手绘磨损、机械身体语言和荒唐工程因果。风格化不是低面数、平涂或把所有东西做成圆角玩具；每个夸张部件都要说明一个工程动作、危险方向或笑点。

### 1.2 高精度

高精度指作者化的结构、拆件、枢轴、材质、贴图、灯光、动画和镜头一致性，不等于写实或堆三角形。正式资产必须能从概念图追到 Blender 源、材质层、状态表、动作事件、碰撞代理、LOD、Godot 实机截图和缺陷复测。

### 1.3 去 AI 感

不得用随机细节、连续噪声、泛光、通用科幻面板或“看起来很完成”的表面掩盖没有作者意图的问题。禁止：

- 随机铆钉、随机管线、无功能的 greeble、无法解释的漂浮件；
- 贴图文字、箭头、概念板边框和错误拼写直接烘进模型；
- 左右结构、材质尺度、关节方向和阴影逻辑互相矛盾；
- 融合活动件、没有枢轴的机械臂、穿插的液压件和不可读的碰撞包络；
- 只换颜色或只加发光就声称产生了新模块、新敌人或新阶段。

每件资产必须有设计意图表：主形、功能件、负形、动作件、材质分区、喜剧细节、反例和人工复核记录。

### 1.4 多样成长与百种构筑

首发构筑规划以 **100 个可区分的 build 作为起步下限**。这里的 build 是玩家在一局中能感到不同操作节奏、目标优先级、路线选择和机器轮廓的构筑身份，不是 100 个颜色变体或数值排列。

每个 build 至少要有：

1. 一个主技能机制：改变输入节奏、空间关系、载荷、路线、修复关系或形态规则；
2. 一个决策成本：热量、冷却、装载、暴露、转向、资源、位置或反制窗口；
3. 一个视觉证据：车体拆件/负形/动作至少有一项结构变化，另有一套可读的 VFX/材质/声音状态；
4. 一个 UI 证据：卡面、图标、预览对比和实战提示能说清“怎么做、付出什么、结果是什么”；
5. 一个反制或失败原因：玩家能知道为什么成功、失败和下一局如何调整；
6. 一个存档身份：装配、阶段、载荷、修复或永久奖励恢复后，build 不会变成另一个构筑。

## 2. 百种构筑的机制骨架

先用机制家族组织差异，再组合成 build。每个家族至少规划 10 个真正不同的变体；变体必须通过行为测试和视觉样板，不得靠改名或换色达标。

| 机制家族 | 主要改变 | 视觉表现方向 | 代表变体示例 |
|---|---|---|---|
| 聚拢/磁吸 | 目标分布、质量门槛、投掷路线 | 磁环、吸附轨迹、被拉动的挂件与车体线圈 | 轻件打包、轨道牵引、极性反转、范围锚定 |
| 水/电状态 | 状态铺设、连锁、危险区域 | 水膜、导电线、跳弧、湿润材质与短促放电 | 单点导电、链式回路、湿地导流、过载断路 |
| 惯性/冲撞 | 行驶蓄势、碰撞次序、路线风险 | 飞轮、轮迹、受力变形、冲撞余韵与碎片方向 | 直线冲锋、回弹反冲、侧滑推墙、刹车爆发 |
| 载荷/压缩 | 装载资格、分类、释放时机 | 腔体开合、载荷层级、压缩形态和投掷姿态 | 鲸口打包、分类投递、过载抛洒、精准释放 |
| 钻掘/地形 | 穿越路线、地下窗口、地块状态 | 钻头、地表裂线、土石飞散、出入口标记 | 直线钻穿、短潜伏、地脉抬升、钻孔传送 |
| 变形/折叠 | 工作区、移动规则、碰撞和路线 | 新负形、展开关节、阶段显隐和镜头避让 | 颚口展开、桥体折叠、移动工厂、护盾展开 |
| 修复/建设 | 战场状态、补给、捷径、永久世界结果 | 维修件、压力表、流水、植被、灯光与远景变化 | 泵站修复、桥梁重建、导流、营地服务 |
| 诱导/反制 | 预告方向、敌人行为、空间陷阱 | 假目标、工单标记、反向箭头、延迟动作残影 | 诱导冲锋、复制动作、错误施工、反向工单 |
| 热量/节奏 | 爆发窗口、冷却、持续暴露 | 温度色阶、蒸汽、过热件、冷却液和停机姿态 | 短爆发、蓄热炮、过热护甲、冷却换位 |
| 经济/回收 | 废料选择、蓝图、风险回报、持久成长 | 分类仓、蓝图板、回收标签、修复后的服务设施 | 高价值拆件、蓝图赌注、废料转能、回收反哺 |

100 个 build 的第一版目录应记录：`build_id`、机制家族、输入节奏、核心模块、辅助模块、形态阶段、成本、反制、视觉拆件、VFX/SFX、UI 说明、测试场景、存档字段和状态。目录未完成前不把“内容量”写成已实现。

## 3. 构筑的成长层

- **基础层**：一辆车、一项工程动词、一个清楚的代价。玩家 60–90 秒内能试出结果。
- **分支层**：第二个模块改变路线、节奏或空间，而不是只加输出。
- **组合层**：两个或多个模块通过状态、载荷或事件形成第三种行为，并有独立视觉签名。
- **形态层**：阶段变化增加负形、关节、工作区或移动规则；驾驶室和身份锚点仍可认出。
- **合同层**：构筑必须能处理普通目标、修复设施和首领；不同 build 通过不同工程解法完成同一合同。

每次成长都要同时更新三张表：功能状态表、视觉状态表、UI 解释表。只更新数值或卡面而不更新机器结构，视为未完成。

## 4. 正式资产与白模的界线

当前 Godot 程序几何、旧 GLB、Weaver 候选和低质量渲染全部是 `whitebox` / `study`。它们只能验证碰撞、输入、流程、状态、存档和镜头问题，不能成为正式资源或商店素材。

正式资产必须经过：概念图对照 → 作者化建模/贴图 → 状态与动作 → Godot Mobile 材质/灯光/镜头 → 无 VFX 实机图 → 有 VFX 动作图 → 720p/1080p 与性能检查 → 缺陷复测。通过前一关才能进入下一关。

## 5. 全局验收问题

每次新增模块、敌人、设施或 UI 状态，都要回答：

- 玩家是否能在真实镜头中一眼读出主形和工程动词？
- 关闭 VFX、贴图和声音后，危险、目标、退路和解法是否仍然成立？
- 机制是否改变了操作、路线、节奏、空间、修复或形态？
- 视觉、UI 和声音是否对同一个权威事件给出一致解释？
- 这是否是一个新 build 身份，还是一次换色/加数值/换文案？
- 读档、暂停、低画质和手柄流程是否保持同一结果？

任何一个答案为否，资产或 build 只能留在 `whitebox`、`proposal` 或 `candidate`，不能标记为 `integrated` 或 `final`。
